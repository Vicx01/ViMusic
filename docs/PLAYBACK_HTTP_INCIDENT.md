# Investigation: Media3 error 2000 and Ktor ClientRequestException

## Evidence and limitations

The reported `ExoPlaybackException → UnexpectedLoaderException → ClientRequestException` is a class chain, not an HTTP trace. The actual failing video, request, HTTP status, response body, headers, redirect history, and device logs were not supplied. There is no evidence that the earlier 512 KiB fix resolved this incident, nor that a signed audio URL had even been obtained. Sandbox attempts to reach the providers failed at TLS/DNS, which says nothing about the user's device. Do not infer a particular 4xx, provider rejection, URL expiry, bitrate, time, or track from this chain.

In this checkout `ClientRequestException` is Ktor **2.1.2**, not Media3 or OkHttp's audio exception. With `expectSuccess = true`, Ktor's [default validator](https://github.com/ktorio/ktor/blob/2.1.2/ktor-client/ktor-client-core/common/src/io/ktor/client/plugins/DefaultResponseValidation.kt) throws it for a **400–499 response**. It extends Ktor `ResponseException`, which extends `IllegalStateException`; its original message includes method, full URL and response text. Ktor does not set an underlying cause for this response exception; do not print or share its raw message or a full stack trace. A 200 response with `playabilityStatus` set to a failure is a different path.

When a cache/URL-ring miss causes Media3 to open the app's `ResolvingDataSource`, `PlayerService` executes `Innertube.player` on `Dispatchers.IO`, and `Result.getOrThrow()` propagates the Ktor exception on the Media3 loader thread. Before this change, [Media3 1.0.0-beta03 Loader](https://github.com/androidx/media/blob/1.0.0-beta03/libraries/exoplayer/src/main/java/androidx/media3/exoplayer/upstream/Loader.java) catches non-`IOException` exceptions and wraps them in `UnexpectedLoaderException`. Thus that wrapper is expected from Media3's perspective; it is not evidence of a failure in the audio HTTP client. Its default policy does not retry an `UnexpectedLoaderException`. Media3's player subsequently reports the source error as code 2000 (`ERROR_CODE_IO_UNSPECIFIED`).

Three Ktor requests can fail in this resolver, in order:

1. `POST music.youtube.com/youtubei/v1/player` using the Android profile. A failed HTTP response stops here; it does not trigger the embedded attempt.
2. A second POST to that path using the embedded profile, **only if** the first returned a non-OK playability status.
3. `GET watchapi.whatever.social/streams/{videoId}`, **only if** the embedded response was OK. The video ID is intentionally not logged.

The chain by itself does not identify which one failed. The audio URL is fetched later by Media3 `DefaultHttpDataSource`, not Ktor. Its non-2xx responses normally produce `HttpDataSource.InvalidResponseCodeException`, with a response code, response headers, DataSpec and response body; they do not normally produce Ktor `ClientRequestException`. Range requests are generated by Media3 from the DataSpec, including later cache misses, seeks or retries. The URI-only resolver preserves the incoming DataSpec's position, length and request headers; CacheDataSource and HTTP can form their own upstream ranges. Synthetic server tests cover those behaviors, not a provider's response.

## New, privacy-restricted diagnostics

For Ktor HTTP responses in these three operations, `PlayerRequestException` records a constant stage, HTTP status, final host (only the expected host is named; any other host is redacted), whether the API-key header is present in Ktor's final request metadata, and an allowlisted body summary. Only numeric `error.code`, a small set of known `error.status` values and a small set of known first `error.errors[].reason` values are shown. Other body text, including messages, URLs, identifiers, cookies and tokens, is omitted; unrecognized or over-16-KiB bodies are marked omitted. The original Ktor exception remains the cause for programmatic inspection. **Its raw message and cause chain may contain sensitive data.** Do not dump or send it.

The wrapper is an `IOException`, so Media3 no longer needs `UnexpectedLoaderException` for this HTTP failure. The app's load policy explicitly does not retry this wrapper, preserving the prior policy for Ktor HTTP response exceptions; other I/O exceptions retain Media3's normal retry policy. Errors are not suppressed. The UI and debug `PlaybackError` log show the sanitized stage, status, summary, final host, header-presence flag and cause class names. The audio HTTP failure path separately reports whether the failed DataSpec requested a range, byte position/length, status, and syntactically validated Content-Length, Content-Range and Accept-Ranges; audio response body is omitted. `PlaybackHttp` logs the same safe header fields for successful audio opens.

Media3 itself logs full player/loader exception stacks, which would otherwise include Ktor's URL and body. The service installs a process-wide Media3 logger that replaces the two known `ExoPlayerImplInternal` playback-error and `LoadTask` unexpected-loader stack messages with fixed text; other Media3 log messages pass through. This is not a guarantee that unrelated apps or other library log tags cannot log sensitive data. Filter and review diagnostics before sharing; never send a full unreviewed logcat or exception dump. The cause itself is preserved, not sanitized in memory.

A final host differing from the requested stage's expected host is evidence that the final Ktor response came from another host; a matching host does not rule out same-host redirects. Redirect chains, Location values, full requests, arbitrary response headers and bodies are intentionally not recorded. A range classification describes the DataSpec at the failed HTTP open, not proof of an expired or incomplete URL.

## Static request configuration and open questions

* The shared Ktor client uses the OkHttp engine, browser User-Agent, content negotiation and brotli, with default `Content-Type` and `X-Goog-Api-Key` headers. Ktor's 2.1.2 `DefaultRequest` source merges headers into absolute requests too: the key header is therefore configured for the conditional third-party GET; the default `prettyPrint` query is merged for relative InnerTube URLs but not the absolute GET. This is a cross-origin disclosure risk in the existing configuration, not proof that this user's fallback ran. Ktor's redirect code removes `Authorization` on authority changes but does not explicitly remove this key header. Scope credentials by origin in a separately tested change; do not share key values.
* Ktor's redirect plugin follows GET/HEAD redirects by default, not POST, and disallows HTTPS-to-HTTP downgrade. The OkHttp engine disables its own redirects and enables connection-failure retry. The app does not explicitly configure Ktor `HttpTimeout`. Ktor 2.1.2 declares OkHttp 4.9.3, whose builder defaults are 10 seconds each for connect, read and write, with no whole-call timeout; the resolved runtime version and effective timeouts have not been measured on the device. A response exception proves a response arrived, not a timeout.
* Audio HTTP is configured with 16-second connect and 8-second read timeouts and a fixed Firefox User-Agent. DefaultHttpDataSource normally follows same-protocol redirects and disallows cross-protocol redirects. Actual redirect hops and headers on the user's device are unknown.
* The resolver keeps two direct URLs in memory without checking expiration or automatically invalidating one after HTTP failure. A URL may be rejected or expire, but nothing in the submitted Ktor chain proves either. The original selected format URL may be missing or Piped's exact-bitrate match may fail; neither is established for this incident. No provider, credential, URL or duration was substituted here.

## What to collect to identify the incident

Use the debug APK built from this change on the affected device; reproduce with the same track/network and indicate whether it occurs on first play, after a seek, after cache clearing, or after roughly how many seconds. Capture the error overlay or run `adb logcat -s PlaybackHttp:D PlaybackError:E` around the failure. Share only those reviewed, sanitized lines plus app version/build, Android version, approximate time, and whether cache was cold/warm. Do not send raw URLs, video IDs, authorization headers, cookies, API keys, response messages or raw bodies. The newer stage/status fields identify which resolver request failed, while audio range/status fields identify a media delivery response. If the new safe fields are insufficient, collect additional allowlisted metadata locally; the full original error text is not safe to publish.

The synthetic local emulator and mock HTTP tests are not proof of real-provider behavior. A physical-device reproduction and real provider response remain necessary before choosing a provider-specific compatibility or URL-refresh fix.
